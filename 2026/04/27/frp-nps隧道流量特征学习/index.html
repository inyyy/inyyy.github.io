frp/nps隧道流量特征学习

一：原理

内网穿透/反向代理：攻击者拿下内网主机后，出网一般受防火墙/ACL 限制——外网无法直接连入内网，但内网主机能主动访问外网。frp/nps 这类工具就在受害机（内网）上跑客户端（frpc/npc），让它主动外连攻击者的公网服务端（frps/nps server），建立一条”反向”隧道，把内网端口映射到外网服务端上。攻击者从公网访问服务端映射端口，即可访问内网服务。整个链路方向是”受害者→攻击者”，所以只拦”外部连入”的传统防护拦不住这种流量。

二：frp/nps隧道工具了解

frp是反向代理型工具（Go 编写，fatedier/frp），作用就是搭建隧道，将内网服务的 tcp/udp/http 等流量通过受害机主动外连的 frps 服务端转发出去，默认使用 TCP 通信（服务端 bindPort=7000）。控制通道默认 TLS 加密（新版实测 v0.71 默认开启 transport.tls.enable，应用层不可见），老版本或关闭 TLS 时是 JSON 明文消息，支持 TCP 多路复用、压缩
nps是内网穿透代理型工具（Go 编写，ehang-io/nps），作用与 frp 类似，额外支持 socks5、p2p 等代理方式，npc 主动外连 nps 服务端（默认 bridgePort=8024），管理后台默认 8080，隧道加密可选

三：frp/nps在数据包中的流量特征(结合实际攻击数据包学习放在最后面)

一：frp

frp的工作原理：
1：攻击者在公网部署 frps 服务端（默认监听 7000 端口）
2：受害机运行 frpc，主动向 frps 发起 TCP 长连接完成认证注册；老版本/明文模式下第一条消息是 JSON 格式的 Login，携带 version、hostname、os、arch、user、privilege_key、pool_count 等字段
3：frps 与 frpc 之间维护一条稳定的控制连接，周期发送 Ping/Pong 心跳保活（默认 30s、可配置，本实验配置为 3s）；实际代理数据通过额外的工作连接（Work Connection）传输，控制连接与工作连接分离
4：当有流量访问 frps 映射端口时，frps 通过 ReqWorkConn 请求 frpc 新建工作连接，frpc 将内网服务的响应经该连接回传，实现内外网双向通信

流量特征

1：frp 是长连接 + 周期性心跳，控制连接建立后稳定存在，按固定周期发送心跳（默认 30s、可配置）。本实验配置 heartbeatInterval=3，抓包可见登录突发后进入绝对规律的 3.000s 周期，每个整点一次等长小包突发（加密后 4 条 TLS 记录、每条约 34 字节应用数据）——用 IO Graph 看就是一条精准的周期线，与正常业务流量完全不同
2：老版本/明文模式下（关闭 TLS），首包是 JSON 的 Login 消息，含 "type":"Login"、"version"、"hostname"、"os"、"arch"、"user" 等可读字段，tcp.payload contains "Login" 直接命中——这是老版本 frp 的强特征
3：控制连接与工作连接分离：同一条隧道会看到一条稳定长连接（控制，frpc→frps:7000）+ 多条按需建立的短数据连接（frps:7001 → frpc → 内网服务:8081），访问代理端口时数据连接突发，不访问时只剩心跳
4：新版 frp默认开启 TLS（transport.tls.enable 默认 true），控制通道被 TLS 1.2 加密，首包不再是明文 JSON，tcp.payload contains "Login" 不命中，只能看到 TLS record 头 17 03 03 和固定周期的等长密文——这是「非 443 端口的 TLS 长连接」异常场景，反而成了现代 frp 的检测切入点
5：默认开启 TCP 多路复用（transport.tcpMux）时，控制消息与数据可能复用同一条连接，抓包时按「客户端源端口不变 + 周期心跳 + 突发数据」组合判断，单靠首包格式不可靠

一条46746端口到7000端口的长连接(tcp三次握手之后不会马上四次挥手关闭，长时间保持ESTABLISHED连接状态)，帧数为161，frps的默认端口在frpc的ini配置文件里就是7000,还可以看到它的Duration是12s左右，很长，端口7001是数据隧道，短链接，Duration很短，端口8081和7001时间差不多，因为数据就是从7001进8081出

使用io图表查看，密集过后一条平线搭配一个尖峰，规律性，尖峰部分就是心跳包

第三特征：数据隧道的两个端口同生几乎是同时出现和消失，时间间隔很小的毫秒级，并且间隔时间也很有规律

这里传了一个hello.txt，数据只走工作连接，控制连接主要用于保活

完整特征：

1：先有一个7000端口的tcp连接

2：登录异常（出现一个长连接和一些短连接）

3：先7001端口后8081端口，一先一后，一进一出，连接时长的时间间隔很有规律且包数对应

4：除去短连接其余全是心跳包

利用工具特征辨别：

frp、nps 都是”长连接+心跳”型隧道，区分主要看应用层：老版本/明文 frp 是 JSON 明文消息（Login/Ping/NewProxy），新版 frp 是默认 TLS 的稳定心跳连接（靠周期线识别），nps 未加密时是固定魔术串开头，reGeorg 是 HTTP 内嵌 base64 流量，抓包时对比首包格式即可

二：nps

nps的工作原理：
1：攻击者在公网部署 nps 服务端（默认 bridgePort=8024，web 管理后台 8080）
2：受害机运行 npc，主动向 nps 服务端 bridge 端口发起连接。桥接消息是「长度前缀 + 内容」的帧结构，心跳为固定 7 字节头 + 28 字节 RFC3339 时间戳；网上流传的固定魔术串 INSECURE-CLEAR-TEXT-NPSCP 在实测 v0.26.10 默认抓包里并不存在，多见于早期资料，不能当可靠特征依赖
3：npc 与服务端之间建立 mux 多路复用隧道，控制消息与代理数据复用同一连接，支持 tcp/udp/http/https/socks5/p2p 多种代理方式
4：通信过程中周期性发送心跳包保活，连接长期稳定

流量特征

1：nps 桥接端口默认 8024，管理后台默认 8080，用 tcp.port == 8024、tcp.port == 8080 直接筛
2：未加密桥接没有 INSECURE-CLEAR-TEXT-NPSCP 魔术串，tcp.payload contains "INSECURE-CLEAR-TEXT-NPSCP" 不命中——该说法只出现在早期资料/特定版本。v0.26.10 的真实特征反而是：长度前缀帧 + 7 字节定长头（如 00:ff:ff:ff:ff:1c:00）+ 28 字节 RFC3339 时间戳心跳（每 5s 一组双向），用 tcp.port == 8024 && tcp.len == 28 直接命中时间戳心跳
3：与 frp 一样是长连接+心跳型，连接持续稳定、小包周期保活。桥接里能看到明文 JSON 协商消息（如工作连接 {"ConnType":"tcp","Host":"内网目标","Crypt":false,...}），crypt=false 时转发的数据也是明文（可看到透传的 HTTP）
4：nps 管理后台 8080 有 web 指纹（nps 登录页面特征），内网探测时也可从 web 侧确认
5：默认端口、心跳参数、加密开关都可被改源码/改配置绕过，特征检测是对抗性的，需要配合连接基线和时序分析
